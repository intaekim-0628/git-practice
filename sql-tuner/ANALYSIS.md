# 분석 및 실제 검증 결과

## 원본 학습 코드

1. Oracle v4의 `instruction`·`input`·`answer`는 문자열이 아닌 객체입니다. 원본은 Python `str(dict)`로 지시/정답을 만들고 `input`도 Python repr로 붙여, 재현 가능한 JSON 응답 형식으로 학습하지 않습니다. 새 데이터는 `messages`와 UTF-8 JSON으로 통일했습니다.
2. 원본 `SFTTrainer(dataset_text_field='text')`에는 입력/정답 분리 마스킹이 없습니다. 기본 전체 문자열 loss로 사용자 SQL과 지시까지 학습할 수 있습니다. 새 코드는 실제 chat template의 답변 위치와 tokenizer offset으로 labels를 만들어 입력은 -100으로 마스킹합니다. 120B 모델의 실제 tokenizer와의 런타임 검증은 H200 실행 시 수행됩니다.
3. 고정 steps=100 평가는 작은 데이터에서 epoch 중 한 번도 실행되지 않을 수 있습니다. 새 코드는 epoch마다 평가/저장, best checkpoint 로딩, early stopping, 실제 epoch 분석을 제공합니다.
4. 원본에는 test가 없습니다. 새 코드는 eval로만 모델을 고르고 마지막에 test를 평가합니다.
5. 원본은 3~5시간 예상/측정 로직이 없습니다. 새 코드는 첫 epoch 측정, 예산 상한, epoch 상한을 기록합니다. 현재 자료로 시간 하한을 채우겠다는 주장은 하지 않습니다.
6. 원본의 4096 token 제한은 긴 정답을 절단할 수 있습니다. 새 기본값은 8192이며 조용한 절단을 금지합니다. 토큰 길이는 실제 모델 tokenizer를 로딩한 뒤 확정됩니다.
7. JSON 형식이 맞아도 원본 정답에는 근거가 부족한 DDL, 읽기 어려운 물음표 문자, 확인되지 않은 `after_plan.verified=true`가 있습니다. 정답 재구성 및 원본 보존을 분리했습니다.

## 데이터 결과

JSONL 14개에서 배열을 펼쳐 총 579개 레코드를 검사했습니다. Oracle 소스는 94개 ID에 해당합니다. 12개 C등급과 불완전 SQL 1개를 격리했습니다. 대소문자·공백 증강 134개와 동일 입력/재구성 정답 중복 7개를 제외했습니다. 최종 74건을 39/22/13건으로 분리했습니다. SQL 템플릿 계열은 4/2/2이며 분할 간 동일 그룹이 없습니다.

기존 자료 275건은 정확한 레코드 기준 95종입니다. 메타데이터와 실제 계획이 없고 Oracle 원본 SQL과 AST 기준 정확히 일치하지 않아, 출처를 보존한 전문가 검토 파일로 옮겼습니다. 74개의 재구성 정답에는 자동 생성된 보수적 권고가 포함됩니다. 모두 실제 SQL 전문가/Oracle 실행 검증을 거친 것은 아닙니다. 58건은 원본 DDL·힌트·숨겨진 파라미터 권고를 배제했으며 후보 SQL이 남은 건은 16건입니다.

이는 부족한 근거에서의 응답 통제를 위한 출발점입니다. 실제 인덱스 설계를 가르칠 수 있는 물리 객체 유형 정보가 없어 관련 정답을 학습 가능한 검증 데이터라고 선언하지 않았습니다. 원본은 sources 및 oracle_originals에 그대로 남아 있습니다.

## 현재 클라우드에서 통과한 검증

- 모든 입력 레코드의 JSON 파싱 및 배열 형식 처리.
- 데이터 재구성 실행 성공.
- train/eval/test 그룹 분리 및 messages 스키마 검증.
- 데이터의 DDL 적격성, 미측정 plan 표현, 후보 SQL 파싱 검사.
- 5개 단위 테스트 통과: 분할/정답 검증, 템플릿 식별자 보존, assistant mask 및 절단 거부, 시간 계획/과적합 판정, 생성 결과 실패 검출.
- Python 파일 구문 컴파일, setup shell 구문 검사 통과.

## 실행하지 않은 것

이 환경에는 `nvidia-smi`와 `/dev/nvidia*`가 없고 PyTorch/Unsloth도 설치되어 있지 않습니다. 사용자가 알려 준 H200은 이 세션에 연결된 실행 장치가 아닙니다. 따라서 120B 모델 로딩·QLoRA 업데이트·epoch 평가·Oracle SQL 실행은 하지 않았습니다. requirements 전체 설치 및 실제 Harmony tokenizer 검증도 수행하지 않았습니다. CPU 단위 테스트의 문자 tokenizer는 마스킹 로직만 검증합니다.

실제 epoch 수치나 학습 완료 어댑터는 이 패키지에 없습니다. H200에서 실행하면 학습 로그와 평가에 근거한 보고서를 생성합니다. 설치 의존성은 H200 런타임에서 해석/검증하고 runtime-lock.txt에 저장하도록 했으며, 현재 파일을 완전히 검증된 GPU 환경이라고 표현하지 않습니다.

## 사용자 요청에 따른 추가 증강

기존 train을 유지하며 최대 20개 변형/부모를 생성했고, 중복 제거 후 591건을 확보했습니다. 552건이 합성 예제입니다. 동일 SQL의 요청 표현과 형식 변형, 계획 누락, 인덱스 정보 누락, 소유자 정보 누락, SQL 단독 입력을 포함합니다. 각 입력의 객체 분류와 관측 계획 정답은 수정된 근거에 맞춰 다시 구성했습니다. 근거 제거 변형에는 원본 재작성 권고를 재사용하지 않았습니다.

eval/test는 바이트 수준으로 유지했습니다. 증강 데이터에도 원본 group_id를 보존하고 holdout과 교차하지 않는지 확인했습니다. AST 보존, 중복 제거, 원본 유지, 변경된 근거와 정답의 일치 검사를 추가해 총 7개 단위 테스트가 통과했습니다. 증강 파일의 데이터 로더 검증도 성공했습니다. GPU 학습은 여전히 실행하지 않았습니다.
